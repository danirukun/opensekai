# Scene performance monitor analysis

The Scene window renders evaluated preview frames through a pump that runs at display rate. The pump renders only the newest frame, and it skips a display frame while a submission is in progress. Operators need a quick measure while they tune scenes for live output. The existing frame acknowledgment reports CPU submission time but does not provide a visible trend. A stats.js overlay can show the preview's completed-frame rate and submission duration without changing the renderer or native protocol.

The monitor belongs to the Scene window. The separate transparent OBS output must stay free of UI. The control should default to off, remember the operator's choice locally, and stop measurement when hidden. A frame begins immediately before preview `applyFrame` and ends when that promise settles. This measures the preview submission path, including occasional asset loading. It does not measure GPU execution or OBS frame rate. The built-in memory panel can be unavailable in WKWebView.

The session publishes at 60 Hz, so the preview cannot show more than 60 FPS. On 2026-10-09 the pump changed from a fixed 15 Hz timer to display frames. With the 15 Hz timer, the monitor showed at most 15 FPS for every scene, and operators read that value as an avatar cost. The preview FPS value cannot be used as the concert or output FPS benchmark. WebKit pauses display frames when the Scene window is minimized; the OBS output does not use this pump. The overlay is a development aid; output performance still needs separate benchmark evidence.
