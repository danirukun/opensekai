# lilToon on WebGPU analysis

Date: 2026-11-19. Scope: [#269](https://github.com/danirukun/opensekai/issues/269) (spike) and [#74](https://github.com/danirukun/opensekai/issues/74) (MAT-02), slice 1. MAT-03 ([#75](https://github.com/danirukun/opensekai/issues/75)) and `.warudo` import come later. Context: [character lighting](2026-11-19-character-lighting.md), which this slice follows. Source: [design](../../docs/superpowers/specs/2026-11-19-liltoon-webgpu-design.md), [plan](../../docs/superpowers/plans/2026-11-19-liltoon-webgpu.md).

## Problem

1. **A VRM export loses the lilToon look.** Many VTuber avatars (VRChat and Booth models) use the lilToon shader in Unity. In Unity and in Warudo they show toon shadow bands, a rim light, a matcap, and an outline. UniVRM changes each of these materials to MToon on export. The look is lost.
2. **OpenSekai has no lilToon material.** OpenSekai draws a VRM material with `CharacterMToonMaterial`. It has one shadow band. It has no second or third band, no lilToon rim, no backlight, and no matcap blend.
3. **The existing lilToon loader does not run on WebGPU.** three-liltoon draws lilToon in WebGL 2 only. OpenSekai uses `WebGPURenderer` and its light rig. The loader cannot be used as it is.
4. **The owner wants the look that users expect from Unity or Warudo.** The Unity result is the reference. An MToon version of the same avatar is not the reference.
5. **The result must hold on the OBS output.** The output is a transparent premultiplied image. A lilToon material must not add a halo, a gray veil, or a background alpha above 0.

## Current state

- **The owner library has no lilToon avatar.** All eight VRM files are VRM 0 and use `VRM/MToon` only. Only one `.warudo` bundle contains lilToon. `.warudo` import is a separate project and is not in this slice. Thus this slice needs a sample avatar that carries lilToon data.
- **three-liltoon 0.1.9** is a library of `mochiya-labs` (MIT).
  - It draws in WebGL 2 only. `LilToonMaterial` is a `RawShaderMaterial`. Its GLSL is cross-compiled from the lilToon 2.3.4 HLSL through DXC, SPIR-V, and SPIRV-Cross. Its `FEATURE_MATRIX` lists WebGPU as unsupported.
  - It reads the glTF extension `MOCHIYA_materials_liltoon`, spec 1.3. The fields are `specVersion`, `lilToonVersion`, `shaderVariant`, `properties`, `textures`, and `cubeTextures`.
  - The repository commits `dist/`. The directory `src/generated/` is git-ignored and is generated by `npm run generate`. A git dependency thus gets the built `dist/` and does not need the shader tools.
  - It reports `materialWarnings` for features that it does not support.
- **`WebGPURenderer` takes node materials only.** A `RawShaderMaterial` does not work there. A WebGPU lilToon material must be a TSL `NodeMaterial`.
- **Material parameter control (B38) has the read side only.** `materialReport`, `materialEntries`, and the MCP tool `material_list` exist. The write operation `setMaterialValues` does not exist in the code. A `liltoon` profile thus needs no write guard in this slice. The editable lilToon values are a later slice.
- **The Rust import check reads only `extensionsRequired`.** `check_required` in `apps/desktop/src-tauri/src/assets/mod.rs` compares each entry with the list `VRM_REQUIRED`. It does not read `extensionsUsed`. A name in `extensionsUsed` passes today. A name in `extensionsRequired` that is not in `VRM_REQUIRED` fails the import.
- **Character lighting is in place.** `CharacterMToonMaterial`, `CharacterShare` (the room fill), the `characters` light group, and the avatar Lighting group exist. A lilToon material must use the same light group and the same share.
- **Light limits (B34b).** 8 lit lights and 2 shadow lights. Each lit-light add stalls the Editor while the lit materials compile. The character lighting gate is: not more than 20 % longer than the reference at 8 lit lights. This slice replaces that gate for lilToon with a warm limit (see Decisions).

## Decisions

- **Port core lilToon to TSL in a fork (owner, 2026-11-19).** `LilToonNodeMaterial` in a fork `danirukun/three-liltoon`, branch `webgpu`, entry `@mochiya/three-liltoon/webgpu`. It uses the property names, defaults, and texture rules of three-liltoon. TSL compiles on WebGPU and on the WebGL 2 fallback. The cost: the equations are ported by hand and can drift from upstream.
  - Rejected: a WGSL output of the SPIR-V build. `WebGPURenderer` takes only node materials, so this needs a backend patch. It also loses the WebGL 2 fallback and the OpenSekai light rig.
  - Rejected: a map of lilToon onto `CharacterMToonMaterial`. It loses the second and third shadow bands, the matcap, and most of the look.
- **The slice has a fixed feature list.** Main color and texture with `_MainTex_ST`; light limits; first, second, and third shadow; normal map (first); rim; backlight; matcap (first); emission (first); opaque, cutout, and transparent variants; outline variants. Every other enabled feature gives an `unsupported-feature` warning that names the lilToon property. The load never fails because of a missing feature.
- **Toon bands for the main light only (owner decision, 2026-11-20).** Unity lilToon uses toon shading for the main light and adds the other lights in a simpler way. The port does the same. The main light is the first directional light of the light set. If the set has no directional light, it is the first lit light. "First" is the order in which the renderer made the lights, not the entity order. The main light gives the shadow bands and the backlight. Each other light adds its color, times its cast shadow, to the summed light color, with no bands. The first port gave each light its own bands. That made the shader grow with each light: 1.84 million WGSL characters at 8 lit lights against 0.24 million for MToon, and a 14.7 s Editor stall at a spot add against 8.1 s for MToon. The cause of the stall is the Metal compile in the WebKit GPU process, which blocks the next synchronous WebGPU call (`GPUBuffer.getMappedRange`). An asynchronous precompile and one shader module for each WGSL source did not make it shorter.
- **The stall gate is warm (owner decision, 2026-11-20).** The owner accepts a first compile of some seconds, if the runtime after it is quick. WebKit compiles each new render pipeline in about 0.4 s, and the time does not change with the light type or the WGSL size. WebKit keeps the compiled shaders on disk, and identical WGSL compiles again in about 5 ms, also after an app restart. Thus the long stall occurs one time for each light set on a computer. The gate is the warm stall: the time from the light add to the GPU completion of the first frame at the new revision, after a run that compiled the same light sets. The limit is 250 ms (15 frames at 60 FPS) in the Editor preview and on the OBS output. The cold stall and the ratio to the MToon Catboy are recorded and do not fail the check. The time to the first frame alone is not the stall: an MToon frame can be sent while the GPU process still compiles for 6 s.
- **Light units need a scale.** The light limits clamp the summed light color. OpenSekai light intensities are not Unity units. The port multiplies the light color by `UNITY_LIGHT_SCALE`. The start value is `1 / Math.PI`. The calibration sets the final value so that one directional light at the default intensity gives the Unity face level.
- **The indirect terms mirror `CharacterMToonMaterial` (controller ruling).** `CharacterLilToonMaterial` gets the room fill and the ambient share with the same terms and the same constants as `CharacterMToonMaterial`. It does not use new numbers.
- **The Lighting group applies in part.** Environment Fill scales the room fill. Shadow Strength scales only the cast shadow from the shadow map (`mix(1, shadow, shadowStrength)`). It does not change the authored bands. Rim Strength, Rim Width, and Rim Tint have no effect, because a lilToon material has its own rim and backlight. The OpenSekai back-light rim is not added.
- **A GLB prop with the extension loads on the PBR path (controller ruling).** The slice is for VRM avatars. A GLB that is not a VRM and has the extension loads with the PBR material as it does now. The load warning names the extension.
- **The lilToon extension wins over MToon.** A VRM material with both the extension and MToon data gets the lilToon material. No MToon material is made for it.
- **The `liltoon` profile has no editable values.** `materialReport` and its Rust copy get the profile `liltoon`. It is in `material_list` and in the Inspector with no parameter. `MOCHIYA_materials_liltoon` is a known extension for a VRM material. The Rust check accepts it in `extensionsUsed`, and in `extensionsRequired` when the exporter puts it there.
- **The sample avatar is made in Unity.** Catboy gets lilToon materials in Unity 6000.0.71f1 with UniVRM 0.131.4 and lilToon 2.4.1. Mochiya Avatar Tools exports the file. If the exporter does not accept the avatar, a UniVRM export plus a small script writes the extension. The evidence records the path. The Unity project and the export stay outside the repository.
- **The evidence has three captures.** One directional light and one camera in each. Reference 1 is the Unity Game view. Reference 2 is the upstream three-liltoon viewer in WebGL. The third capture is OpenSekai on WebGPU. When reference 1 and the MToon version differ, reference 1 decides.
- **One branch, one PR.** This is MAT-02 slice 1. It merges to `main` with the spec-first rules. The #269 decision (continue, defer, or stop) is about the next slices, not about this one.

## Effects

- A VRM avatar with `MOCHIYA_materials_liltoon` shows the lilToon shadow bands, rim, backlight, matcap, emission, and outline in the preview and on the OBS output. It uses the OpenSekai lights and the room fill.
- A VRM without the extension loads as it does now. The MToon path does not change.
- `material_list` shows `liltoon` materials. A material that uses a feature outside the slice gives a load warning.
- The Rust import check accepts a VRM that names the extension.
- The repository gets one new dependency, the fork at a fixed commit. `ARCHITECTURE.md` and `docs/dependencies.md` change in the same commit.

## Risks

- **The look can drift from Unity.** The equations are a hand port and the main light is chosen by a rule (the first directional light, else the first lit light), not by the Unity light settings. The three captures and the owner look check are the gate.
- **Light units.** If `UNITY_LIGHT_SCALE` is wrong, the face is too bright or too dark. The calibration against reference 1 is the control.
- **Compile cost.** Only the main light adds shadow bands to the shader; each other light adds a color term. The sample has 24 render pipelines that change with the light set, against 13 for the MToon Catboy, so the first compile of a new light set is longer for lilToon (about 15 s against 7 to 10 s in the Editor preview). A warm stall longer than 250 ms at 8 lit lights is a failure. A light set at the limit must not fail with `Pipeline compile failed`.
- **Newer lilToon.** The sample uses lilToon 2.4.1. three-liltoon was made against 2.3.4. A property that the fork does not know is recorded and is not drawn.
- **The exporter.** It is documented for VRChat and Modular Avatar prefabs. It can refuse the re-imported Catboy. The fallback is the UniVRM export plus the script.
- **A dependency on a fork.** The fork can drift from upstream. It has a pinned commit and a `dist/` that is built and committed.
- **Outline and alpha.** An outline of a cutout or transparent material can show a halo on the OBS output. This needs the check over dark, light, and checker backgrounds.
- **GPU time is unknown** until #305. The cloud run has only software adapters, so a look claim needs the owner check on macOS.
- **Three internals.** The material depends on the `LightingModel` and node interfaces of the pinned three r187. A version change must run the renderer tests again.

## Out of scope

- `.warudo` import. It is a candidate with a selection gate, and the rights review comes first.
- Fur, gem, refraction, refraction blur, the two-pass transparent mode, and the lilToon Lite and Multi variants. These are MAT-03.
- Pixel parity with Unity. The result is approximate.
- Editable lilToon values in the Inspector, in MCP, and in Blueprint (B38, MAT-08).
- lilToon on a GLB prop or on an environment.
- A VRM expression bind on a lilToon material. The bind gives a warning.
- A publish of the fork to npm, and a pull request to upstream.
- Windows, and GPU time.
