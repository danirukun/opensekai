# REASONS: Video screens

Date: 2026-11-08. Scope: MED-02 slice 1. A Screen whose content is one MP4 or WebM video from the asset library. The session owns the playback position. Each renderer client plays the video in sync, the OBS page plays its audio, and each client reports a codec that it cannot decode. Analysis: [video screens](../analysis/2026-11-08-video-screens.md). Issue: [GitHub #60](https://github.com/danirukun/opensekai/issues/60). Base: [image screens](2026-11-04-image-screens.md) (B28).

## R — Requirements

### Asset record

R1. `AssetRecord.format` adds `mp4` and `webm` in TypeScript (zod) and Rust. The record adds the optional group `video: { width, height, durationMs, videoCodec, audioCodec, alpha }`:
- `width` and `height`: integers 1 to 4096.
- `durationMs`: integer 1 to 14,400,000 (4 hours).
- `videoCodec`: `h264 | hevc | vp8 | vp9 | av1`.
- `audioCodec`: `aac | mp3 | opus | vorbis | null`.
- `alpha`: boolean.

TypeScript (`AssetRecordSchema`) and Rust (`AssetRecord` `Validate`) apply the same cross-field rules:
- A video format needs `video`, an ID with the `video_` prefix, `expressions` empty, no `image`, and no `rig`, `eyeBones`, or `meshes`.
- `mp4` allows `videoCodec` `h264`, `hevc`, or `av1` and `audioCodec` `aac`, `mp3`, `opus`, or `null`. `webm` allows `vp8`, `vp9`, or `av1` and `opus`, `vorbis`, or `null`.
- `alpha` is true only for `webm` with `vp8` or `vp9`.
- Any other format has no `video` and no `video_` ID.
- Old records validate without change.

`fixtures/protocol/video-records.json` holds valid and invalid records, and a test on each side reads it (as `image-records.json` does).

R2. The ID of a video record is `video_` plus the SHA-256 of the stored bytes. The library file extension is `.mp4` or `.webm`, and the registry library load uses the same table as B28 R2. `AssetSummary.kind` adds `video` (TypeScript and Rust), from the `video_` prefix. A video record has `licenseLabel: "User supplied"`, `sourceUrl: null`, `importerVersion: 1`, and no `credits`.

### Import

R3. A new editor-only Tauri command `import_video` opens a native dialog. The title is `Import video`. The filter is `Video` with `mp4`, `m4v`, and `webm` (no filter label on macOS). The frontend never sends a path. The command returns the record, and the host sends the `asset-record` event. The command is in each place that `import_image` is (B28 R3): `build.rs`, `permissions/autogenerated/import_video.toml`, `capabilities/main.json`, `generate_handler!`, the exact permission list test, the ports trait in `bootstrap.rs`, and `DesktopState::import_video` with the same `AssetStep` hooks.

R4. `assets/video.rs` has one pure function `parse_video(bytes) -> Result<VideoHeader, AppError>` (format, width, height, durationMs, videoCodec, audioCodec, alpha). It reads container structure only. It does not decode a frame. It uses no new crate. It finds the type from the signature only, not from the file extension. Each rule reads only inside the buffer and checks each length before use. Each failure is `INVALID_INPUT` with a message that names the type and the reason. The rules are:
- **MP4 (ISO BMFF):**
  - The first box is `ftyp`. Its major brand is not `qt  `.
  - A box size is a big-endian u32. Size 1 reads a u64 large size. Size 0 runs to the end of its parent. A size below the header size or past the parent end is a failure.
  - Walk the top-level boxes across the whole file. Exactly one `moov` is necessary. A box with an unknown type is skipped.
  - `moov/mvhd` (version 0 or 1) gives the timescale and the duration. A timescale of 0 or a duration of 0 is a failure (a fragmented MP4 without a duration is not supported).
  - For each `moov/trak`: `mdia/hdlr` gives the handler (`vide` or `soun`). `mdia/minf/stbl/stsd` gives the first sample entry type.
  - The first `vide` track is the video. Its sample entry `avc1` or `avc3` is `h264`, `hvc1` or `hev1` is `hevc`, and `av01` is `av1`. Another entry (for example `mp4v`, `vp09`, or an encrypted `encv`) is a failure.
  - Its `tkhd` (version 0 or 1) gives the width and height (16.16 fixed point, integer part) and the matrix. A matrix that turns 90 or 270 degrees swaps width and height. A matrix that is not a turn by a multiple of 90 degrees is a failure.
  - The first `soun` track gives the audio: `mp4a` is `aac` when its `esds` object type is 0x40, and `mp3` when it is 0x69 or 0x6B. `Opus` is `opus`. Another entry is a failure. No `soun` track gives `null`.
  - Each `dref` entry in each track must have the self-contained flag (flags bit 0). An entry without it (an external data reference) is a failure.
  - `alpha` is false.
- **WebM (Matroska with DocType `webm`):**
  - The file starts with the EBML ID `1A 45 DF A3`. The EBML header `DocType` is `webm`. Another DocType (for example `matroska`) is a failure.
  - Element IDs and sizes use the EBML variable-length rules (IDs up to 4 bytes, sizes up to 8 bytes). An unknown size is allowed only for `Segment` and `Cluster`.
  - In `Segment`, walk the children until `Info` and `Tracks` are read, or until the first `Cluster`. The walk reads at most the first 16 MiB.
  - `Info` gives `TimecodeScale` (default 1,000,000 ns) and `Duration` (a 4- or 8-byte float). A missing or non-positive duration is a failure.
  - The first `TrackEntry` with `TrackType` 1 is the video. `CodecID` `V_VP8` is `vp8`, `V_VP9` is `vp9`, and `V_AV1` is `av1`. Its `Video` element gives `PixelWidth` and `PixelHeight`. `DisplayWidth` and `DisplayHeight`, when present with the default `DisplayUnit` 0, replace them. `AlphaMode` 1 sets `alpha`.
  - The first `TrackEntry` with `TrackType` 2 is the audio: `A_OPUS` is `opus` and `A_VORBIS` is `vorbis`. Another codec is a failure. No audio track gives `null`.
  - A `ContentEncodings` element in the video or audio track (encryption or compression) is a failure.
- No video track is a failure with the message `Video has no video track`. A size or duration outside R1 is a failure.

R5. The import first checks the file metadata length. A file above 256 MiB fails with `INVALID_INPUT` and the message `Video is larger than 256 MiB`. The stage step copies the file to a temporary library file in 1 MiB chunks and hashes it at the same time. It reads the file into memory one time to run `parse_video`, then drops the buffer. The record name is the file stem, cut by `bounded_name`, or `Video` when the stem is empty. The same bytes return the existing record through `AssetRegistry::commit`. `stage_video` stages without the registry lock, as `stage_image` does.

### Serve and trust

R6. `read_located` adds a branch for the video formats. It runs `parse_video`. The detected format, width, height, duration, codecs, and alpha must equal `record.video`. `GET /assets/{id}` answers `video/mp4` or `video/webm` with `x-content-type-options: nosniff`. The size and SHA-256 checks do not change. The service sends no `Range` or `accept-ranges` response in this slice.

R7. `ARCHITECTURE.md` changes in the same commit. The trust rule now names a third container type: one MP4 or WebM file whose container structure the host checks at import and at serve (`parse_video`), with no external data reference, and whose signature the renderer checks at load (R13). Asset path steps 1, 2, and 4 name the video import, the serve check, and the video load. The renderer paragraph names the video playback rule (R12 to R15) and the OBS audio rule (R16).

### Scene and session

R8. `ScreenContentSchema` adds `{ kind: 'video', assetId: Id | null, autoPlay: boolean, loop: boolean, volume: number }` (`volume` 0 to 1) in TypeScript and the Rust `ScreenContent`. A scene has at most 4 screens with video content (`LIMITS.videoScreens` in the `SceneViewSchema` refine and `MAX_VIDEO_SCREENS` in the Rust `SceneView::validate`), inside the B28 limit of 16 screens. A show without a video screen validates without change.

R9. The operation `setScreenVideo { entityId, video: { assetId, autoPlay, loop, volume } }` sets `content` to `{ kind: 'video', ...video }`. `setScreenImage` (B28 R9) sets image content on a screen with video content. Both fail with `NOT_FOUND` for an unknown entity and with `INVALID_INPUT` for an entity that is not a screen. A `setScreenVideo` that makes a fifth video screen fails with `INVALID_INPUT`. The operation is in `PatchOpSchema`, `LivePatchOp`, and the Rust `PatchOp`. The session does not check that the asset exists or that it is a video (as B28 R9).

R10. The live operation `controlScreenVideo { entityId, action: 'play' | 'pause' | 'restart' }` changes only runtime state. It does not commit and does not change the revision. It fails with `NOT_FOUND` for an unknown entity and with `INVALID_INPUT` for an entity that is not a screen with video content. It is in `PatchOpSchema`, `LivePatchOp`, and the Rust `PatchOp`.

R11. The session keeps one runtime playback entry for each screen with video content: `{ playing, anchorMs, offsetMs }`. `anchorMs` is the session `elapsedMs` at the last play or restart, and `offsetMs` is the position at that time. The position is `offsetMs + (elapsedMs − anchorMs)` while playing and `offsetMs` while paused.
- A new entry starts with `offsetMs` 0 and `playing` equal to `autoPlay`. A new entry starts when a screen gets video content, when its `assetId` changes, when a show opens, and when a Duplicate makes a copy.
- A change of `autoPlay`, `loop`, or `volume` does not change the entry.
- `play` sets `anchorMs` to now and keeps `offsetMs`. `pause` stores the current position in `offsetMs`. `restart` sets `offsetMs` to 0 and `anchorMs` to now and keeps `playing`.
- The entry is removed when the screen is deleted or its content is no longer video.
- The entry is never saved or put in a show file. Undo of a scene patch does not change it, except through the rules above.

Each frame has the optional field `screenPlayback: [{ entityId, playing, positionMs }]` (at most `LIMITS.videoScreens` entries, unique IDs, `positionMs` a non-negative integer) for each screen with video content and a non-null `assetId`. `positionMs` is not wrapped: the renderer applies `loop` and the duration (R14). `RuntimeFrameSchema` and the Rust frame type both accept the field.

### Renderer

R12. Each renderer client (OBS page, scene pane preview, editor viewport, and screenshot) draws one quad for each visible screen with video content, a non-null `assetId`, and a loaded video. The quad rules of B28 R11 apply: 1 m high, `width / height` m wide, local XY plane, facing +Z, `DoubleSide`, the front upright and not mirrored, and the back mirrored. `width` and `height` are `videoWidth` and `videoHeight` of the loaded element (the display size after the container turn). The material rules of B28 R14 apply: unlit, `toneMapped: false`, no shadows, and not in a light group.

R13. Video loading:
- The renderer reads the bytes with `readAsset`. It checks the signature with `videoFormatOf` in `video-screen.ts`: an MP4 `ftyp` box at offset 4, or the EBML ID with DocType `webm`. A GLB, a VRM, an image, or another file is a failure. The host check of R6 makes sure that the rest equals the record.
- It makes one `Blob` with the type `video/mp4` or `video/webm` and one object URL for each asset in one renderer client. When no screen uses the asset, it revokes the URL. The asset IDs are in the `used` set and in `retainOnly`.
- It makes one `HTMLVideoElement` for each screen (two screens with the same asset have their own position). The element has `playsInline`, `preload: 'auto'`, `loop: false`, `crossOrigin` unset, and is not in the DOM tree. Its `muted` and `volume` follow R16.
- The texture is a three.js `VideoTexture` with `colorSpace` sRGB and the same UV and flip rule as B28 R12, so the front is upright on WebGL 2 and WebGPU.
- The load succeeds at the element `loadeddata` event. An element `error` event, or no `loadeddata` within 10 s, is a failure.
- The element is paused and the texture does not update while the screen is not visible.

R14. Playback sync, on each applied frame, for each screen with a `screenPlayback` entry and a loaded element:
- `duration` is the element `duration` in ms. The target is `positionMs mod duration` when `loop` is true, and `min(positionMs, duration − 1 frame)` when it is false.
- When the entry is playing, the target is before the end, and the element is paused, the renderer calls `play()`. When the entry is paused, or the end is reached without `loop`, it calls `pause()`.
- When the distance between `currentTime` and the target is above 250 ms (on a loop, the shorter way around the end), the renderer sets `currentTime` to the target. A paused entry always seeks to its target when they differ by more than 1 frame (1/60 s).
- The renderer does not change `playbackRate`. It does not start a second seek while one is running.
- A rejected `play()` promise (an autoplay block) gives the frame warning `Video playback blocked`. The renderer tries again on the next playing frame.
- The screenshot (`cameraScreenshot`) draws the current texture of each client. It does not wait for a seek.

R15. Load failures use the load jobs with a new `LoadRequest.kind` `video`. The failure messages are:
- `Video codec not supported: H.264`, `HEVC`, `VP8`, `VP9`, or `AV1`, when `canPlayType` for the format and the codec family answers `""`, or the element error code is `MEDIA_ERR_SRC_NOT_SUPPORTED` or `MEDIA_ERR_DECODE`. The renderer finds the codec family from the container, with the same sample entry and `CodecID` rules as R4. It reads only the boxes or elements that it needs.
- `Video failed to load` for each other failure: an unknown asset, a record of another kind, a bad signature, a read failure, and the 10 s timeout.

The frame warning is `Asset load failed: <message>`, and the Inspector failure message is `<message>`. A failed job retries under the existing rule (a newer revision and 3 s). A failure draws nothing for that screen and does not stop the other entities. A loading video gives the existing `Asset loading` warning. The asset ID branch in `renderer.ts` handles a video screen explicitly. A video is never read as a mesh or an image.

R16. Audio: only the OBS page (`apps/output`) plays audio. Its elements have `muted: false` and `volume` from the content. The scene pane preview, the editor viewport, and the screenshot client always set `muted: true`. A video without an audio track plays the same way.

R17. Transparency: a video whose element shows alpha draws with the B28 R15 rules (`transparent: true`, normal blending, `depthWrite: false`, straight alpha). The renderer reads the alpha flag from the WebM `AlphaMode` (with the R15 container read). Each other video draws opaque. The output alpha rule of B28 R15 applies on the direct canvas path, on the post chain, and in a `cameraScreenshot` PNG.

R18. A video screen is a viewport pick target, and the transform gizmo moves, rotates, and scales it (as B28 R16).

### Editor

R19. The Inspector **Screen** section gets a **Content** select with **Image** and **Video** before the source field.
- Image shows the B28 **Image** field.
- Video shows a **Video** field with the same form: a select of the video records, the `Import file…` row, the load status, and the failure message. The empty option is `Choose video…`. An unknown `assetId` shows `Missing video`.
- Video also shows **Auto Play** (checkbox), **Loop** (checkbox), **Volume** (slider 0 to 1), and the playback buttons **Play** or **Pause** (one button that follows the frame `playing` value) and **Restart**.
- A change of Content to Video sends `setScreenVideo` with `assetId: null`, `autoPlay: false`, `loop: true`, `volume: 1`. A change to Image sends `setScreenImage` with `assetId: null`. Content Video is disabled at the video screen limit, unless the screen already has video content.
- A video record option sends `setScreenVideo` with the other values unchanged. Auto Play, Loop, and Volume send `setScreenVideo`. Play, Pause, and Restart send `controlScreenVideo`.
- `Import file…` runs `import_video` through a new `chooseVideo` handler in `EditorApp.svelte`. A returned record sends `setScreenVideo` for that screen only. A cancelled dialog keeps the value. An import error shows the host message, or `Could not import video` when it has none.
- The Inspector reset (B17) covers Content (default Image), Auto Play (false), Loop (true), and Volume (1). The section index covers the section.
- The Assets list shows video records with their format and video codec.

R20. Regression tests: the Prop, Environment, character, and Screen Image selects do not list video records. The Screen Video select lists only video records. The Add menu **Screen** item does not change (it still makes image content).

### MCP and files

R21. MCP `scene_patch` accepts `createEntity` with a video screen, `setScreenVideo`, and `controlScreenVideo`. `asset_list` returns video summaries with `kind: 'video'`. The `asset_list` description names `setScreenVideo`. The `scene_patch` description says how to play a video. `app_status` does not change. There is no MCP video import.

R22. Save As and Open keep each video screen and its saved content. After Open, playback follows R11 (`playing` equals `autoPlay`, position 0). A screen whose `assetId` is not in the library opens and shows `Missing video`.

## A — Approach

Add one asset kind, one content member, one saved operation, and one runtime operation. Reuse the B28 paths at each step. The host checks the container structure and serves the file with the existing bearer read. The renderer plays the file from a `Blob` URL, so no token goes into a URL and the service needs no `Range` support. The session is the one clock: it puts the position on each frame, and each client corrects its element only when the drift is large. Only the OBS page makes sound. No video data goes through Tauri IPC.

## N — Norms

- Use `@oshi-connect/ui` controls.
- Keep UI copy to the labels in R3, R15, R19, and R22.
- Write prose in ASD-STE100.
- Use pnpm.
- Keep functional TypeScript and plain data.
- Store the video metadata as one nested group on the record (constitution rule 7).
- Do not commit third-party media.

## S — Safeguards

- Do not loosen the GLB or image trust checks.
- Do not put a token in a URL. Do not add a `Range` endpoint in this slice.
- Do not send video bytes, frames, or audio through Tauri IPC.
- Do not make the renderer the clock owner. A renderer never changes the session position.
- Do not change the look of a scene without a video screen. Its frames have no `screenPlayback` field.
- Do not add a Rust media crate, a native decoder, or a new vendor.
- Do not claim these from this slice: HEVC alpha, MOV or Matroska, streaming, Blueprint playback, audio in the Editor window, OBS audio sync, decode cost on a real GPU, or Windows support.
- An old build does not open a show with a video screen. Record this in the evidence.
