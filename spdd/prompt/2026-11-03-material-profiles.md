Status: implemented on `claude/b27-mtoon-pbr-impl`. Cloud evidence: [material profiles check](../../docs/evaluation/material-profiles.md). Owner checks on macOS remain.

## R — Requirements

1. **Material report.** `materialReport(json)` in `packages/contracts/src/materials.ts` reads the glTF JSON of the stored file and returns `{materials, asset}`. The renderer gives it the JSON that `inspectContainer` reads from the GLB bytes before `parseAsync`, because the three-vrm v0compat plugin replaces the VRM 0.x entries of `parser.json.materials` during the parse. `materials` has one entry for each entry of `json.materials`, in index order: `{index, name, profile, unsupported}`.
   - `name` is the trimmed material name, or `Material <index>` when the name is empty or missing. It is cut to 64 UTF-16 units without a cut surrogate pair.
   - `profile` is `mtoon` when the material has `VRMC_materials_mtoon`, or when the file has `extensions.VRM.materialProperties[index].shader === 'VRM/MToon'`. It is `unlit` when the material is not `mtoon` and has `KHR_materials_unlit`, or when its VRM 0.x shader starts with `VRM/Unlit` (the v0compat rule). Otherwise it is `pbr`.
   - `unsupported` is a sorted list of unique feature names, each cut to 64 units, each one of:
     - each key of `material.extensions` that is not in `MATERIAL_EXTENSIONS` (R2);
     - for an `mtoon` material, each key of `material.extensions` other than `VRMC_materials_mtoon`, `KHR_materials_unlit`, `KHR_materials_emissive_strength`, and `VRMC_materials_hdr_emissiveMultiplier`, because MToon does not read the PBR extensions;
     - `shader:<name>` when the file has a VRM 0.x material property for this index whose `shader` is a string that is not `VRM/MToon`, does not start with `VRM/Unlit`, and is not `VRM_USE_GLTFSHADER`. A property without a `shader` string adds nothing; v0compat then keeps the glTF material;
     - `KHR_texture_basisu` when a texture of this material has that extension and has no core `source` (three.js then has no image; with a core `source` it uses that image). Texture references are the base color, metallic roughness, normal, occlusion, and emissive textures, and each object with an `index` key inside a material extension object.
   - `asset` is the sorted list of root `extensionsUsed` names that a material cannot carry but that change the material look and that the loader does not read: `KHR_materials_variants`.
   - The function does not throw on a malformed shape. A missing or wrong-typed field counts as absent.
2. **Supported lists.** `MATERIAL_EXTENSIONS` holds the material extensions that the pinned three 0.180.0 `GLTFLoader` and three-vrm 3.5.5 read: `KHR_materials_anisotropy`, `KHR_materials_clearcoat`, `KHR_materials_dispersion`, `KHR_materials_emissive_strength`, `KHR_materials_ior`, `KHR_materials_iridescence`, `KHR_materials_sheen`, `KHR_materials_specular`, `KHR_materials_transmission`, `KHR_materials_unlit`, `KHR_materials_volume`, `EXT_materials_bump`, `VRMC_materials_mtoon`, `VRMC_materials_hdr_emissiveMultiplier`. A test pins the list: it reads the material-level names (`KHR_materials_*`, `EXT_materials_*`) from the source text of the installed `GLTFLoader.js` (the `EXTENSIONS` object is not exported), and the `VRMC_*` names from the `EXTENSION_NAME` of the installed three-vrm material plugins. A version change that adds or removes one fails the test.
3. **Load warning.** At each asset load (avatar, prop, and environment), `assets.ts` runs `materialReport` on the JSON of the bytes (R1). When at least one entry has a non-empty `unsupported`, or `asset` is not empty, the load result gets one warning `{code: 'UNSUPPORTED', message, ids: [assetId]}`. The message is `Unsupported material features: ` followed by `<material name> (<features joined by ', '>)` for each such entry (at most 8 features, then `, and <n> more`), joined by `; `, at most 16 entries, then `; and <n> more` when more exist, then `; asset (<asset features joined by ', '>)` when `asset` is not empty. Because each name and feature is cut to 64 units (R1) and an entry lists at most 8 features, the message has a fixed upper size. The model still loads, and three.js keeps its fallback for each such material. The warning goes with the other load warnings into each frame acknowledgment of each client that draws the asset, so `app_status` shows it in `outputs[].lastFrame.warnings`. The renderer does not change a material because of the report.
4. **VRM required extensions.** The VRM import (`registry.rs`, in the function that reads the GLB and calls `validate_humanoid`, next to the version check) rejects a VRM whose `extensionsRequired` names an extension that is not in the shared `SUPPORTED_REQUIRED` list, `VRMC_vrm`, `VRMC_springBone`, `VRMC_node_constraint`, `VRMC_materials_mtoon`, `VRMC_materials_hdr_emissiveMultiplier`, or `VRM`. The error is `Unsupported required extension: <name>`, the same text as the scene import. The two importers use one list in Rust, moved to `assets/mod.rs`. The shared list adds `EXT_materials_bump` and `EXT_texture_avif`, which the three 0.180 loader reads, so the scene import accepts them too. A record that is already stored is not checked again.
5. **MToon UV animation.** Each renderer client sets the UV animation values of each material in `vrm.materials` (three-vrm `gltf.userData.vrmMToonMaterials`, which holds the surface materials and their outline clones) of each loaded avatar from the frame time, on each applied frame, before it draws. This covers the loop over installed avatars and an avatar that is installed in the same frame. The node material reads the values through `materialReference`, so a property write is enough: with `t = frame.elapsedMs / 1000`, `uvAnimationScrollXOffset = sx × t`, `uvAnimationScrollYOffset = sy × t`, `uvAnimationRotationPhase = r × t`, where `sx`, `sy`, `r` are the speed factors of the material. Each value then wraps (R6). The values are absolute, not a sum of deltas, so two clients that apply the same frame have the same values. Each material uses its own speeds; an outline material is a clone of its surface material, so it has the same speeds and the same values. A material whose three speeds are 0 is not changed. The renderer does not call `VRM.update` (spring bones stay off, CHR-08).
6. **Wrap rule.** When the material has a `uvAnimationMaskTexture`, no value wraps, because the shader multiplies the scroll and the phase by the mask after the wrap. Otherwise the rotation phase wraps into [0, 2π). A scroll value wraps into [0, 2) only when each texture that is set on the material and that the shader samples through the animated UV (`map`, `normalMap`, `emissiveMap`, `shadeMultiplyTexture`, `shadingShiftTexture`, `rimMultiplyTexture`, `outlineWidthMultiplyTexture`) has, on both axes, `RepeatWrapping` with `2 × repeat` an integer, or `MirroredRepeatWrapping` with `repeat` an integer, and a texture `rotation` of 0 (a rotated transform turns the scroll axes); otherwise no scroll value wraps. `matcapTexture` and the mask use the plain UV and do not count. The function `uvAnimationValues(speeds, wrap, t)` in `packages/renderer/src/mtoon-uv.ts` gives the three values and is pure. `uvWrapPolicy(material)` in the same file gives `wrap` from the material once at load.
7. **Fixture check.** A headless check loads `fixture_vrm_1`, `fixture_vrm0_arkit`, `fixture_glb_stage`, and `fixture_test_stage` with the real renderer in Chromium, once with WebGPU and once with WebGL2 on the software adapter (`chromiumGpuArgs`), and draws one frame of each with a transparent clear. For each run it records the backend, the adapter, the material count by profile, the `UNSUPPORTED` warnings, and the pipeline compile failures (`pipeline-diagnostics.ts`). It passes when each fixture loads, each run has no pipeline compile failure, the counts by profile are `fixture_vrm_1` 13 `mtoon`, `fixture_vrm0_arkit` 16 `mtoon`, `fixture_glb_stage` 25 `pbr`, `fixture_test_stage` 11 `pbr` and 1 `unlit`, and no fixture has an `UNSUPPORTED` material warning. The script is `docs/evaluation/material-profiles/headless-check.mjs`, with `chromiumGpuArgs` from `scripts/gpu-probe.ts`, as the earlier headless checks. It writes one PNG for each fixture and backend into `docs/evaluation/material-profiles/` as functional evidence only. A render of the private `fixture_vrm0_arkit` is permitted as evidence (docs/testing.md, Fixtures); the model file is never committed. Without the fixtures, the check reports each missing fixture as skipped, not passed.
8. **Known gaps**, not in this slice: a versioned material descriptor on the asset record; MToon look parity on a real GPU and in OBS with alpha (blend and cutout); outline width under render scale and output sizes; MToon with shadows; `KHR_texture_basisu`, Draco, and meshopt decoders; `KHR_materials_variants` selection (reported only, R1); `KHR_materials_pbrSpecularGlossiness` (reported only); MToon support for PBR extensions (reported only); lilToon and NiloToon (MAT-02 to MAT-06); material property control (MAT-08, CHR-07); spring bones (CHR-08).

## E — Entities

- `MaterialProfile = 'mtoon' | 'unlit' | 'pbr'`.
- `MaterialReportEntry = {index: number, name: string, profile: MaterialProfile, unsupported: string[]}`. `MaterialReport = {materials: MaterialReportEntry[], asset: string[]}`.
- `MATERIAL_EXTENSIONS: ReadonlySet<string>` and `TEXTURE_DECODERS_MISSING: ReadonlySet<string>` in `materials.ts`.
- `UvSpeeds = {x: number, y: number, rotation: number}`, `UvWrap = {scroll: boolean, rotation: boolean}`, `UvValues = {scrollX: number, scrollY: number, rotation: number}` in `mtoon-uv.ts`.
- Rust: one `const SUPPORTED_REQUIRED` and a VRM extension list in `assets/mod.rs`, used by `scene_import.rs` and the VRM import in `registry.rs`.
- No change to the scene, show, patch, frame, or asset record schemas.

## A — Approach

- Contracts: `materials.ts` with `materialReport` and the lists; export from `index.ts`.
- Renderer: `inspectContainer` also returns the parsed JSON; `assets.ts` runs the report on it and adds the warning (R3). `mtoon-uv.ts` gives the pure values and the wrap policy (R6). The avatar binding (`createAvatarBinding` in `avatar-pose.ts`) keeps `vrm.materials` and their wrap policies from load. `renderer.ts` sets the values from `frame.elapsedMs` (R5) in the loop over installed avatars and for an avatar installed in the same frame.
- Host: move `SUPPORTED_REQUIRED` to `assets/mod.rs` and add the two extensions; `registry.rs` checks `extensionsRequired` in the VRM import next to the version check (R4).
- Evaluation: `docs/evaluation/material-profiles/headless-check.mjs`, built like `docs/evaluation/fps-counter/headless-check.mjs`, writes the record and the PNGs (R7).

## N — Norms

Functional TypeScript and plain data. Match the compact style of `assets.ts`, `mtoon-binds.ts`, and `scene_import.rs`. No new UI and no UI copy; the warning text is diagnostic data (constitution principle 1). Unit tests for the pure report and the UV values; renderer tests at the real loader; a Rust test at the import boundary; no test of static copy. Prose follows ASD-STE100.

## S — Safeguards

- Do not refuse to load a stored model because of the report. Do not replace or edit a material because of the report.
- Do not drive UV animation from the renderer wall clock or a delta sum. Use `frame.elapsedMs`.
- Do not call `VRM.update` or turn on spring bones or constraints.
- Do not send image data through Tauri IPC on the output path.
- Do not add a decoder (Draco, Basis, meshopt) or a new dependency in this slice.
- Do not claim MAT-01 or a look on macOS, a real GPU, or OBS from the cloud run. The MToon look on the OBS output with alpha, the outlines, and a UV-animated model need an owner check on macOS (`accept:local`). MAT-01 stays unchecked.
