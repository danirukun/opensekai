# REASONS: VMC sender

Analysis: [VMC sender](../analysis/2026-10-21-vmc-sender.md). Issue: [#67](https://github.com/danirukun/opensekai/issues/67) (MED-09). Queue bundle B21.

## R — Requirements

1. A scene can hold at most 4 entities of kind `vmcSender`. Each has the entity base (`id`, `name`, `visible`, `transform`) and `vmcSender: {enabled, address, port, avatarId}`. `enabled` is a boolean. `address` is an IPv4 or IPv6 address (the tracking `ip` rule) that is not unspecified (`0.0.0.0`, `::`), not multicast (`224.0.0.0/4`, `ff00::/8`), and not the limited broadcast `255.255.255.255`. `port` is an integer from 1 to 65535. `avatarId` is an ID or `null`. When `avatarId` is not `null`, it must name an avatar entity in the scene, or the scene fails validation.
2. The patch operation `setVmcSender {entityId, vmcSender}` replaces the settings. It fails with `INVALID_INPUT` and the entity ID when the entity is not a VMC sender. `createEntity`, `renameEntity`, `removeEntity`, and `setVisibility` work as for the other kinds. `setTransform` on a sender fails with `INVALID_INPUT`, as for a tracking source. `removeEntity` of an avatar sets `avatarId` to `null` on each sender that names it, in the same patch, as it clears tracking references. A fifth sender makes the scene fail validation. `visible` has no effect on sending. The Blueprint property registry gives the kind no target, and `REFERENCE_KINDS` does not change. Duplicate (`makeEntityCopy` in `editor/asset-management.ts`) sets `enabled: false` on the copy, as it does for a tracking source. When the session takes a scene from `sceneReplace` (show Open) or as its start scene, it sets `enabled: false` on each sender before the first frame, so a show file never starts a send. A `scenePatch` from the editor or MCP can enable a sender; MCP uses the same API as the editor.
3. TypeScript and Rust validate the same shape, the same limit, and the avatar reference. The validation vectors (target `scene`) have a valid sender, a fifth sender, port 0, port 65536, a port that is not an integer, a bad address, the addresses `0.0.0.0`, `::`, `239.0.0.1`, `ff02::1`, and `255.255.255.255`, and an `avatarId` that names no avatar. Target `call` has a valid and a wrong-shape `setVmcSender` patch.
4. The Add Asset menu has "VMC Sender". The new entity is named "VMC Sender", visible, with the identity transform, disabled, address `127.0.0.1`, port 39539, and the first avatar of the scene or `null`. One helper `vmcSenderLimitReached(entities)` disables the menu item and the Hierarchy Duplicate action at the limit, with the existing "Scene asset limit reached" title.
5. The Inspector of a sender shows Start or Stop (as the receivers), IP Address, Port, and Character (`Select` of the avatars and None). It shows the status state and the error text from `appStatus`, as the receivers do. It has no Transform section and no Visible box, as a tracking source. Reset to default (B17) uses the values in requirement 4 for IP Address and Port. Character has no reset mark, because its add default depends on the scene (implementation decision, B21 PR). The Hierarchy shows senders in a new group "VMC Senders", after "VMC Receivers", with one icon from the existing icon set.
6. An avatar `AssetRecord` gets an optional `rig: {metaVersion: '0' | '1', restPositions, identityRest}`. `restPositions` holds the glTF local translation of each humanoid bone node that the VRM names (at most 55), keyed by `HUMANOID_BONES` names. For VRM 0 the keys use the thumb remap that `assets/vrm.rs` already does (`ThumbProximal` to `ThumbMetacarpal`, `ThumbIntermediate` to `ThumbProximal`). `identityRest` is `true` only when each humanoid bone node has an identity rest rotation and each ancestor node of `hips` has an identity rotation and a scale of 1. The VRM import fills `rig`. At startup the registry fills it for each avatar record that does not have it, from the stored file, and writes the record again with the existing atomic write. The host makes fixture avatar records with the same reader. A failure leaves the record without `rig` and logs the asset ID. TypeScript and Rust validate the same shape.
7. The session makes the sent pose with one pure function `vmcSendPose(pose, rig)`. It repeats the order of `avatar-pose.ts` `apply` in data, with the rest rotation as identity (the Warudo rule):
   - Normalized step. Start with the `baseBones` rotations and positions, with the VRM 0 sign `(-x, y, -z, w)` and `(-x, y, -z)` when `rig.metaVersion` is `'0'`. Fold `chest` into `spine` when `rig.restPositions` has no `chest` (`resolveChest`: spine rotation times chest rotation, chest position turned by the spine rotation and added). Then for each `bones` entry with space `normalized`, without a sign: the target is `spine` when the name is `chest`, the rig has no `chest`, and `bones.spine` is not `normalized`; slerp the target rotation from the current value to the tracked value by `weight` (default 1), and lerp the position when the tracked value has one. Fold again. Then each `boneOffsets` entry whose bone is not `raw` in `bones` multiplies on the left, with the VRM 0 sign, `spine` before `chest`, and a `chest` offset goes to `spine` when the rig has no `chest`.
   - Raw step. For each `bones` entry with space `raw`: start from the normalized-step value of the bone, or from identity and the rest position when `baseBones` is absent; slerp the rotation to the tracked value by `weight`, and lerp the position to the tracked position when it has one (any bone, not only `hips`). Then each `boneOffsets` entry whose bone is `raw` multiplies on the left, with the VRM 0 sign.
   - Positions. A bone without a position from these steps sends its rest position. A `normalized` position is a delta: it adds to the rest position. A `raw` position replaces it. As in the renderer (three-vrm `VRMHumanoidRig.update` moves only the hips), only the `hips` takes a `normalized` position delta (implementation decision, B21 PR).
   The result is `{root, bones, blends}` in the OpenSekai (three.js, right-handed) convention of the raw rig, for each bone in `rig.restPositions`. `root` is the pose root or the identity at the origin. `blends` is `pose.expressions` with the VRM 1 preset names changed to the VRM 0 clip names: the reverse of the preset part of the renderer alias table (`happy` to `Joy`, `angry` to `Angry`, `sad` to `Sorrow`, `relaxed` to `Fun`, `aa` to `A`, `ih` to `I`, `ou` to `U`, `ee` to `E`, `oh` to `O`, `blink` to `Blink`, `blinkLeft` to `Blink_L`, `blinkRight` to `Blink_R`). Other names do not change. A name with a NUL character or more than 128 bytes is left out.
8. On each tick that makes a frame, for each enabled sender whose avatar exists and has a record with `rig.identityRest` true, the session sends one pose in one `vmcPoses` envelope to the host after the frame: `{kind: 'vmcPoses', sessionId, tick, poses: [{senderId, root, bones, blends}]}`, at most 4 poses. When the avatar has no pose in the frame (idle off and no tracking), the pose is the rest pose: identity rotations, rest positions, the identity root, and no blends. Warudo also sends a character that does not move. When no sender qualifies, the session sends nothing. The envelope is never part of the frame and never goes to a renderer.
9. The host accepts `vmcPoses` only from the publisher connection, with the same byte limit as a frame. It checks the shape with the Rust mirror. It drops a pose whose `senderId` is not an enabled sender of the latest accepted scene, or whose sender has an error.
10. The host sender manager (`apps/desktop/src-tauri/src/vmc_sender.rs`) reads the senders on each accepted scene revision, as the tracking manager reads the sources. For each enabled sender it binds one UDP socket on the unspecified address of the target family, port 0. A bind error puts the sender in `error` with the text. A disabled or removed sender closes its socket.
11. Loop guard: a sender is in `error` with "Endpoint used by <name>" and sends nothing when an enabled VMC receiver in the same scene has the same port and the sender address is a local address of this computer: any address in `127.0.0.0/8`, `::1`, the receiver bind address, or an address in the host `localAddresses` list. The guard ignores the receiver `senderAddress` filter on purpose, so it can stop more than a real loop. The pure function `sender_conflicts(senders, receivers, local_addresses)` makes this check and has unit tests.
12. Encoding: the host converts each value to Unity with the exact inverse of the decoder in `parser.rs`: position `(x, y, -z)`, rotation `(-x, -y, z, w)`. Bone names are the VRM 0 / Unity names that the decoder accepts, with the decoder thumb mapping reversed (`leftThumbMetacarpal` to `LeftThumbProximal`, `leftThumbProximal` to `LeftThumbIntermediate`, and the same on the right) and the first letter in upper case. Each datagram is one OSC bundle (`#bundle`, time tag 1) of at most 1,200 bytes and at most 32 messages. The first bundle starts with `/VMC/Ext/OK 1` (`i`) and `/VMC/Ext/T <seconds since the sender started>` (`f`), then `/VMC/Ext/Root/Pos`. Then `/VMC/Ext/Bone/Pos` for each bone, in `HUMANOID_BONES` order. Then `/VMC/Ext/Blend/Val` for each blend, in name order. The last bundle ends with `/VMC/Ext/Blend/Apply`. Floats are `f`.
13. Rate: the host sends a pose for a sender only when at least 15 ms passed since the last sent pose of that sender. It drops a pose that comes earlier. Thus a 60 Hz tick with jitter keeps each pose, and a burst cannot send more than about 67 poses each second. A send error counts in `errors` and does not stop the sender.
14. `appStatus` gets an optional `vmcSenders: [{entityId, state, datagrams, errors, error}]`, at most 4. `state` is `stopped` (disabled), `waiting`, `sending`, or `error`. `waiting` means enabled, with no character, or with no pose from the session in the last 1 s (for example the Scene window is closed); `error` is `null`. `sending` means a pose was sent in the last 1 s. `error` has a text: a bind error, the loop guard, "Character rest pose unknown" (the record has no `rig`), or "Character rig not supported" (`identityRest` is false). The host knows the records, so it sets the two character errors itself. `datagrams` and `errors` are counts since the sender started. TypeScript and Rust check the same shape.
15. Round trip: the bytes that the encoder makes for a pose decode with the OpenSekai VMC decoder to the same raw bones and root (each component within `1e-6 × max(1, |value|)`, for f32 rounding), and to the blends with the sent (VRM 0) names, because the decoder keeps names as they are. A unit test proves it for bones, thumbs, root, blends, and a pose with 55 bones and 64 blends that needs more than one datagram. Each datagram also passes the decoder limits (8 KiB, 64 messages). The 1,200 bytes count the bundle header and the size field of each element.
16. MCP `scene_patch` documents `createEntity` with kind `vmcSender`, `setVmcSender`, the fields, the limit, and that the sender starts disabled. `app_status` returns `vmcSenders`. No new MCP tool.
17. Known gaps, not in this slice: **Send to VirtualMotionCapture**, **Calibrating (VirtualMotionCapture)**, VMC tracker, HMD, controller, camera, and light addresses, rigs with initial bone rotations that are not 0 (they get the error, not a send), a rotated non-humanoid node between two humanoid bones (`identityRest` checks only the humanoid nodes and the ancestors of `hips`, so such a rig sends a wrong pose; found in the B21 review), the axis convention of a real receiver for a VRM 1 rig (the sender sends the raw rig frame for both versions; only the OpenSekai round trip is exact until the owner checks a real receiver), a send while the Scene window is closed (the session stops), and Windows.

## E — Entities

- `VmcSenderSettings`: `{enabled: boolean, address: string, port: number, avatarId: Id | null}` (zod `VmcSenderSettingsSchema`, Rust `VmcSenderSettings`).
- `SceneEntity` gains `{kind: 'vmcSender', vmcSender: VmcSenderSettings}` on the entity base. `LIMITS.vmcSenders = 4`.
- `PatchOp` gains `{kind: 'setVmcSender', entityId, vmcSender}`.
- `AvatarRig`: `{metaVersion: '0' | '1', restPositions: Record<string, Vec3>, identityRest: boolean}`, keys from `HUMANOID_BONES`. `AssetRecord.rig?: AvatarRig`.
- `VmcSendPose`: `{senderId: Id, root: {position: Vec3, rotation: Quat}, bones: Record<string, {position: Vec3, rotation: Quat}>, blends: Record<string, number>}`. At most 55 bones and 64 blends.
- `VmcPosesEnvelope`: `{kind: 'vmcPoses', sessionId: Id, tick: number, poses: VmcSendPose[]}` (at most 4).
- `VmcSenderStatus`: `{entityId: Id, state: 'stopped' | 'waiting' | 'sending' | 'error', datagrams: number, errors: number, error: string | null}`.

## S — Safeguards

- Do not send from a renderer, the Scene preview, or the OBS page. The send path is session to host to UDP.
- Do not put `vmcPoses` into a frame or relay it to a renderer or an operator.
- Do not start a sender enabled from Add, Duplicate, or a show file. Do not send to an address that the operator did not set, or to an unspecified, multicast, or broadcast address.
- Do not send into an enabled VMC receiver of the same app (requirement 11).
- Do not send zero positions in place of rest positions. A sender without `rig`, or with `identityRest: false`, is in `error` and sends nothing.
- Do not add a new crate for OSC. The decoder already reads OSC; the encoder sits next to it.
- Do not claim MED-09 on macOS, with a real VMC application, or on Windows from the cloud run. A real receiver, the send cost, and a send that continues while the Scene window is minimized need an owner check (`accept:local`).
